# Test player manager

The optional Qt `test_players` tool creates and manages a reusable multiplayer
population on an explicitly test-enabled MainSvr. It defaults to 50 characters
and eight guilds. Counts can be changed to 0–500 characters and 0–100 guilds.
The dedicated multiplayer server still uses PostgreSQL; the tool never opens
its database directly.

## Build

Use the existing [multiplayer setup](Multiplayer.md) for PostgreSQL, server
configuration, TLS and optional local game data. Build the tool, matching
server and graphical client together:

```bash
cmake -S . -B build-test-players \
  -DOPENKAL_WITH_POSTGRES=ON \
  -DOPENKAL_BUILD_TEST_PLAYERS=ON \
  -DOPENKAL_ENGINE=gl
cmake --build build-test-players --target test_players openkal_mainsvr openkal_client -j
```

The tool requires Qt 6.9 Widgets. Set `CMAKE_PREFIX_PATH` to the local Qt prefix
when CMake cannot find it. Compatible user-supplied game data remains optional
for building and testing; opening the graphical game view requires the same
runtime data and profile as the normal client.

The desktop application is `bin/tools/test_players`. The separate
`tests/openkal_test_player_integration` executable is an automated test, not the
desktop application; without its PostgreSQL test environment it exits with code 77.

## Start

Stop an older MainSvr before starting the rebuilt server on the same port.
Set a test-control token of at least 16 characters in the server's environment:

```bash
export OPENKAL_TEST_CONTROL_TOKEN='OpenKalLocalTestControl2026'
./build-test-players/bin/openkal_mainsvr
```

In another terminal, start the tool with the same token:

```bash
export OPENKAL_TEST_CONTROL_TOKEN='OpenKalLocalTestControl2026'
./build-test-players/bin/tools/test_players
```

The token can also be entered in the tool. It is not saved in Qt settings or
passed to a child on the command line. Leaving the server token unset disables
all test-control operations. This facility deliberately bypasses ordinary
registration limits, guild founding fees, rank quotas and invitation consent
for managed test identities. Normal account and guild operations retain their
existing rules. Use it only on the intended test server.

Enter the server's IPv4 address, port and trusted CA certificate, then choose
**Connect**. The default local certificate is
`save/multiplayer/tls/server.pem`, generated by the ordinary development server.
The tool preserves certificate verification. Set **TLS server name** when the
certificate identity differs from the connection address.

Choose the active counts and click **Create / update population**. Accounts are
`test0001`, `test0002`, and so on; passwords are `TestPassword0001`,
`TestPassword0002`, and so on. Each account owns one `TestPlayer0001`-style
character. Generated classes rotate through Knight, Mage, Archer and Thief.
New characters use the normal lobby creation transaction, including its configured
starter equipment, spawn, starting vitals and validation. Reusing an existing
character preserves its inventory and does not grant another starter kit.
Passwords use the normal salted password hashing. Initial provisioning can take
a little time while these hashes are calculated.

Repeated preparation reuses existing identities. An account with the reserved
name and a different password, or a conflicting character/guild name, is
rejected instead of overwritten. Increasing the guild count creates additional
guilds. Existing assignments to active guilds are preserved; unassigned players
and members of inactive guilds are distributed over the active guilds. Reducing
counts logs out inactive tool-owned sessions, removes inactive memberships,
and archives extra test guilds outside the live guild catalog. Character records
and archived guild identities remain available for later reuse; restoring a guild
preserves its ID and starts with an empty roster.

## Manage characters and guilds

Use Ctrl or Shift to select multiple player rows. Each row has a **Guild** and
**Role** selector; the right-hand **Guild / character** tab applies membership,
role or level changes to the full selection. Select **No guild** to remove a
membership. Choosing **Leader** transfers leadership; moving or demoting the
current leader elects a replacement when other members remain. Every nonempty
managed guild retains one leader. Temporary, Leader, Sub-Leader, Head Chief,
Chief and Official Member roles map to the existing guild ranks.

Click any player or inventory column heading to sort by it. Click again to
reverse the order. Names and labels sort alphabetically. IDs, levels and
quantities sort numerically. Refreshes keep the sort and selected identities.

Use **Log in selected**, **Log in all** and their logout counterparts to control
real TLS sessions. These clients process incoming packets continuously without
loading graphics or assets. They acknowledge teleports even while a graphical view
is attached. The roster shows login progress, online state, spectator attachment
and the current autonomous activity.
Closing the manager ends its owned sessions.

Click **Move players…** above the roster to open **Move / teleport**. Choose
**Selected players** for a group marked with Ctrl/Shift, **All players** for the
whole roster, or **Guild** and a guild name. The displayed count shows how many
characters will move. Enter the destination map, X, Y and Z/floor height, then
click **Move to destination**. This relocates both online characters and the
saved positions of offline characters.

A repeatable random seed, scatter radius and minimum spacing spread the players
around the target. The default radius is 160 server units and minimum spacing
is 24, suitable for a small spread of the initial 50-player population. A radius
of zero places a single player exactly; multiple players require enough space
for the chosen minimum distance. The server rejects blocked or missing destinations and
checks indoor standing surfaces. Outdoor area maps supply walkability; the
operator supplies the outdoor Z coordinate. Increase the radius or reduce
spacing when the selection cannot fit. Earlier successful changes remain if a
later character cannot be placed; the log reports the failure.

Select one character to inspect inventory. Search the live server's item catalog
by name or definition ID, then give items to the selected characters. Counts and
prefixes are editable grant parameters. Non-stackable items must be granted one
at a time. **Equip** and **Unequip** log in an offline character if necessary and
use the normal equipment rules, including class and level restrictions. Remove
an item after unequipping it. **Refresh inventory** reads current server state.
Item instance IDs and definition IDs are different columns.

## Simulate Castle War

Enable [Castle War](CastleWar.md) with a valid castle layout on your test
server and connect the manager with the server's test-control token. Open the
**Castle War** tab. **Server guilds** lists regular and managed guilds. Filter
by name or use **Refresh guilds** to reload the list. Select a guild and an
alliance, then choose **Set as leader** or **Add as partner**. **New attack
alliance** creates a separate attacking alliance led by the selected guild.
To set up defense, select **Defense alliance** as the destination. A guild can
belong to only one alliance in a simulation.

You can also edit the alliance fields directly. Separate guild names with
commas and place each attacking alliance on a separate line. The first guild
in each alliance leads it.

To take the castle with your usual character, put your guild first in an
attacking alliance and log in with its leader in the normal client. Log in any
test players you want to join through the manager. The server's Castle War
minimum level still applies.

Set shorter declaration, preparation, admission and battle times in seconds.
You can also change the flag-capture delay, the hold time for all four flags
and flag HP. Select **Start simulation**. With automatic admission selected,
the server sends eligible online characters from the chosen guilds to their
camps as soon as admission opens. You can also admit eligible players
manually with **Admit online players** while that window is open. Fight and
capture flags in the normal client. **Finish battle now** settles the current
score using the ordinary winner rules. The tab shows the phase, countdown,
score and simulated castle owner.

**Restore regular schedule** ends the simulation and returns participants to
their entry positions. Simulated ownership, alliances and Castle Honor live
only in memory. The regular settings and saved siege results are retained. A
simulation cannot start during a regular admission window or battle.

## Autonomous play

Autonomous play reads the runtime `config.pak` produced by the build (or installed
with OpenKal). Its item catalog includes the package's merged definitions and
local overrides. It uses the existing **Client profile** selection, including the
normal default / `OPENKAL_PROFILE` when the field is empty, to resolve visual map
paths. Area maps come from `RuntimeData/areas` in the package when available,
otherwise from the profile's `server_map_root`. No separate configuration, area
or visual-map path settings are needed. Catalogs always come from `config.pak`,
including when a development profile names a loose `configuration_root`.
The package and profile must match the running server. Optional user-supplied data
remains runtime input outside the source distribution.

Open **Autonomous play** and choose **Start selected** or **Start all**. Offline
players are logged in through the existing session manager. **Pause selected**
and **Pause all** stop future decisions without logging the characters out.

Each logged-in player owns a dedicated thread for its network session, autonomous
controller and spectator bridge. Slow navigation or network work for one player
does not hold up the other players. Gameplay catalogs are shared read-only;
mutable navigation caches belong to each player. Status changes are sent as value
events and delivered to the UI through queued Qt signals. Activity updates are
sampled once per second; background roster events are combined at up to ten updates per
second so large populations do not flood the UI. Stale events from an earlier
login are discarded. Closing the manager stops and joins all player threads.

Each player processes regular server packets even while paused or watched. The
autonomous controller uses ordinary C2S movement, combat, skill, item, NPC, shop,
quest, rest and revival messages. City travel and the failed-spawn-route fallback
are explicit test-manager exceptions: unlimited city travel and fallback travel
to validated spawn-area destinations use the existing test-control teleport
operation. These operations do not add scroll items or change server validation
rules. Starting autonomy also checks for a class- and level-appropriate weapon.
If none is owned, test control supplies one character-bound weapon from that
class's configured starter kit, and the player equips it through normal gameplay.
An existing suitable weapon, including an unequipped one, prevents another grant.
This recovery does not repeat starter money, consumables or the spawn reset.
A missing starter definition or full inventory produces an explicit error.
Other inventory and progression edits remain operator actions.

Before planning a long outdoor trip, the player chooses the regular city-scroll
destination nearest its goal when that saves more than 1024 walking pixels.
It then walks the remaining local route to the NPC, shop or hunting ground.
The available cities and landing coordinates come from the shared city-scroll
table; there are no NPC-specific teleport coordinates. Travel out of an indoor
map to an outdoor quest city can also use this facility. Each request is queued
once outside the network pump, so its administrative round trip cannot recurse
through the controller. A paused or superseded request is discarded before dispatch.
The player waits for the normal teleport and authoritative position confirmation
before continuing, including while watched. Healing retains priority during the
wait. Rejected requests or missing confirmation pause autonomy rather than retrying
indefinitely or falling back to a long world route. Local movement and dungeon
portal navigation still use the ordinary collision and pathfinding rules.
If the close approach to a visible quest NPC fails or exceeds five seconds of
planning, the player first retries within the server's 64-pixel conversation
range. This allows talking across a blocked shore or an NPC collision mask
without crossing the obstruction. If that route also fails, or a route to a
merchant fails, the player returns to the regular city nearest that NPC and retries
from the confirmed landing point. This recovery is attempted once per NPC route
during an autonomous run; restarting autonomy resets the recovery allowance. A
failed route from the city landing point does not trigger another teleport.

Survival takes priority. Below 60% HP the player attempts an owned healing potion;
below 35% it retreats from nearby combat monsters and recovers to 85% before
resuming. Both manual and Auto-HP medicines use their normal item requests and
shared cooldowns. A safe player may rest; death requests ordinary revival. Mana
potions are attempted below 25% MP. No local inventory or health change is assumed
before a server update.
Once the current fight ends and no recent attacker remains alive, nearby ground
loot is collected before quest travel or another hunt. Recent damage from an already defeated attacker
does not delay collection. Living or unknown recent attackers retain combat
priority, and inventory pressure may require a merchant visit first. Pickup uses
the ordinary item request; ownership, inventory capacity and collection success
remain server decisions.
Every autonomous class enables learned Haste (the normal Z / skill-zero run mode)
as soon as its MP covers the cost, including short approaches and targets already
in range. When a learned run action has no catalog definition, the controller uses
the server's six-MP default; an explicit definition retains its configured cost.
There is no additional 25% MP reserve requirement. Running speed applies
only after server confirmation. Existing Haste buffs are preserved, and rejected requests
are backed off. Characters without an equipped weapon wait instead of hunting;
an owned usable weapon is equipped through normal item requests first.

Available NPC quest transitions are previewed against local copies of the known
quest state using the existing quest evaluator. Preview results are cached until
relevant player state changes. Ready objectives from accepted journal entries take
priority over unrelated new quests. Teleport-only and activity-toggle service
links, including fishing-ground services, do not count as quest progress and do
not attract the player to distant service NPCs. Unsupported actions remain unavailable; each issue
is reported once per loaded catalog with its quest index and flag, including
failures inside linked steps. A raw HTML action without a dialog ID is not guessed. NPC visits and dialog links still
go through the real server. Journal item objectives select matching ordinary or
quest-gated monster loot sources. Otherwise players hunt suitable combat monsters
no more than one level above themselves. Learned targeted combat skills use the
same class, range, MP-cost, precast and cooldown helpers as the graphical client;
other skills and unknown scripted quest behaviors are not guessed.

Movement uses incremental weighted A*, first through centered 32-pixel cells and
locally through eight-pixel subcells near obstacles and narrow passages. Progress
on a long route is retained when refining; a node threshold does not restart the
entire search on a finer grid. Fine neighbors are added only when the sixteen-pixel
neighborhood is constrained, so coarse edges touching a distant riverbank do not
fill the surrounding open ground with fine nodes. The sixteen-pixel check retains
off-grid bridge entrances between coarse cell centers. Coarse
movement that becomes blocked is refined from the confirmed position. Every edge
checks the whole segment and body clearance; diagonal corner cutting is rejected.
Player navigation uses the independent NotMoveable layer, the same standing-point
test as the graphical client, and body-height wall rays. The server-navigation
Blocked layer does not veto player movement. Water-bridge heights come from the
ordinary floor query; each movement height delta must fit the signed packet field.
Every integer movement pixel is checked, including narrow standing obstructions
between the former four-pixel samples. Small validated steps handle tight spots.
Repeated pixel transitions and complete checked segments use bounded static-geometry
caches per player. Unchanged standing poses reuse their resolved heights. Cache keys
include map, incoming height and movement direction; loading another outdoor height
patch or its props invalidates the caches. Distant monster approaches use the ordinary
route validator; the final direct attack segment is checked once the target is in range.
Outdoor standing surfaces include KCM terrain and the same CPU OPL/GB collision
geometry as the graphical client. Neighboring OPL placements are loaded before
standing and movement checks so bridges and walls extending across a map-cell
boundary are included. A reachable bridge deck can span a heightless
blocked area mask under the ordinary client rules; missing geometry and high
roofs do not grant passage. Walls use the existing body-height collision rays.
Indoor navigation uses the shared standing-surface and movement collision checks.
Before planning, the controller aligns stale poses above or below the resolved
standing surface using ordinary zero-horizontal movement packets, at up to 20 Hz
and within the signed Z-delta limit. Each change waits for the server echo; three
rejected corrections pause autonomous play. Loaded bridge decks participate in
the standing query, so a player above a deck settles on it rather than the terrain
underneath.
Healing keeps priority. Missing area or geometry data blocks navigation. Searches
have a node budget and run in small slices with a wall-time budget so they yield to incoming traffic and healing
decisions. Each player thread uses a two-millisecond planning slice independently
of the active population. The allowance is checked between segment validations,
including within a node's neighbor expansion. Unfinished nodes retain their checked
edges across slices. One individual geometry query can still exceed the allowance.
The goal-directed heuristic avoids exploring all equivalent paths across distant
open fields. Planning reports its cumulative expanded-node count, target and grid
spacing and abandons a target after ninety seconds, or five seconds per
hunting-region probe. These bounds also apply near the goal: horizontal distance alone does not predict the cost of a bridge detour.
A pending search retains its frontier until a complete path is found. Explored
prefixes cannot start movement merely because they approach the target: they may
lead to a dead end on the wrong riverbank. Longer checked edges accelerate open
ground without bypassing the segment validator. The selected useful quest destination is
retained until it is completed or invalidated, rather than rescanning every NPC
and portal route on every movement tick. Moving targets, changing combat reach
and redundant position confirmations preserve an in-progress search and its deadline.
Failed searches are remembered at the current origin, so an unchanged quest
route cannot repeatedly displace hunting or other available goals. Moving more
than 32 pixels, a meaningful height correction, a target displacement of more
than 24 pixels, or restarting autonomous play allows a new attempt. If all goals
are unavailable, the status retains the last route failure.

Spawn rectangles describe search regions, not mandatory destinations. The controller
first tries the nearest edge within a conservative portion of the ordinary server
sight range. If no suitable monster appears, stable probes cover the region at roughly
512-pixel intervals. Visible monsters immediately take priority over these probes.
An inaccessible or empty center therefore does not prevent searching the accessible
edge of a large spawn region. Standability is checked before planning. Each probe
has a five-second planning deadline; failures are remembered per probe at the
current origin, so an invalid region cannot restart the same searches indefinitely.
When a standable probe cannot be reached, the manager requests one teleport into
that spawn area instead of returning to a city and starting the same trip again.
The landing point and its resolved height are revalidated with the normal collision
queries. Entirely unstandable regions never become teleport destinations. Requests
are queued outside the game-packet pump and discarded if paused or superseded.
The controller requires matching teleport and authoritative position confirmations,
then gives the new sight snapshot one second to settle before resuming decisions.
NPC visit cooldowns survive teleports. Healing keeps priority while confirmation
is pending; rejection or a fifteen-second confirmation timeout pauses autonomy.
Without a manager fallback callback, failed probes yield to other probes or regions.

Unseen quest NPCs are approached within half the ordinary sight range first, with
a bounded ninety-second search. Once the server reveals the NPC or the player
reaches its vicinity, the controller starts the separate close approach with its
five-second deadline. An obstructed NPC standing point therefore cannot repeatedly
interrupt distant travel with a failed close-range search and a short trip toward
hunting grounds.

NPC conversations normally use the same 24-pixel direct-click range in the graphical
client and controller. Only a failed close approach to a visible NPC permits the
controller's 64-pixel fallback. The conversation retains its selected range;
leaving it, losing the source NPC, or teleporting discards the conversation.
Delayed replies cannot advance quests outside that range. A read-only viewer
keeps a server-approved NPC dialog visible within 64 pixels as well.
After sending an NPC or quest request, the controller waits for a dialog or
quest-state reply before choosing another destination. A five-second reply timeout
pauses autonomy with the NPC index and runtime entity ID in the activity text.
Explicit server rejections for unavailable quest rewards or a full inventory pause
immediately and include the server's reason. Quest rewards using the six medicine
IDs migrated in OpenKal changes #257 and #268 resolve to the owned 23000–23005
definitions only when the requested definition is absent and its replacement is
loaded. An explicitly configured definition takes precedence. This affects
reward insertion only; optional quest files and existing inventory instances are
not rewritten. Unknown rewards still reject the complete exchange, preserving
the delivery item, money and quest progress.
Local dialogs such as revival are independent of NPC proximity. `SendHtml` retains its
four-byte HTML ID and may append a four-byte NPC entity ID. This optional context
lets passive session viewers associate replies with the actual NPC without sending
an interaction themselves; HTML-only consumers and legacy four-byte replies remain
supported.
Navigation waypoints are split into small movement deltas at up to 20 Hz. Distance
is paced using the normal client's walk speed, shared speed modifiers and current
buffs, with fractional distance retained across waypoints. Diagonals use the same
distance budget as straight movement. Stalls cannot accumulate a movement burst.
The player waits for movement echoes, replans after corrections and temporarily
avoids repeatedly rejected or unreachable targets. Authored field portals provide routes between
logical maps; travel still requires walking onto their real trigger tiles.
All reachability questions in one decision share a breadth-first traversal of the
catalog's indexed outgoing portals. Portal failures and cooldown changes invalidate
that result immediately; later decisions reevaluate current availability.

While out of combat, available stat points are spent through ordinary property
requests using these profiles:

- Knight: 50% STR, 40% HTH, 10% DEX.
- Mage: 25% HTH, 25% INT, 50% DEX.
- Archer: 25% HTH, 25% STR, 50% DEX.
- Thief: 50% HTH, 25% STR, 25% DEX.

Percentages apply to spent PU, including the existing increasing stat costs.
Innate class stats and equipment bonuses are excluded. Confirmed base stats
reconstruct prior spending, so restarting autonomy or reconnecting preserves the
distribution. Each single-increment request waits for both its stat and PU reply;
missing confirmation pauses autonomy after five seconds. Unaffordable remainders
are kept for the next intended allocation. Existing points and points earned
after level-ups use the same policy.

After combat, a learned Beheading skill targets nearby kneeling Maguni before
loot or quest travel. The controller observes knee state in spawn snapshots,
GState changes and actions, walks into ordinary weapon-based beheading range,
honors the skill's wind-up and sends one normal cast per corpse. Living attackers
interrupt that preparation; ordinary dead, removed or already beheaded monsters
are excluded. Health and mana restoration remain server-owned.

Ordinary hunting prefers monsters closest to the player's current level within
three levels below through one level above. Lower-level blue mobs are skipped
when matching spawns or visible targets are available, and the controller travels
to a suitable authored spawn instead. Level-ups reevaluate the next target.
An ongoing fight, actual attackers and required quest monsters retain priority.
When no reachable catalog or visible target offers that range, the closest lower
level is used as a fallback.
Among equally suitable visible monsters, each character independently draws a
random entity instead of always choosing the nearest one. Quest type and level
matching remain selection priorities, and actual attackers retain their nearby
defense priority. A selected target is kept while approaching and fighting;
death, removal or an unavailable route permits another draw. Each character owns
its random generator, seeded by character ID, so parallel players do not share a
generator or repeat one common selection sequence.

Usable equipment upgrades are selected by a class-sensitive heuristic using
attack speed, physical or magical damage, defensive stats, primary bonuses,
prefixes and basic talisman bonuses. Complex instance modifiers are retained for
manual review. The conservative heuristic supports ordinary equipment upgrades;
specialized build optimization requires operator decisions.
Replacement waits for unequip/equip confirmations and attempts to restore the old
item if the new one is rejected. With 60 or more general inventory entries, the
player visits a known ordinary merchant and sells obsolete plain equipment until
no eligible excess remains. Worn, bound, premium, quest-required, enchanted and
potentially better equipment is retained. Unknown definitions are retained too.
With manager travel enabled, each selling trip first requests one Narootuh
teleport and waits for its authoritative arrival. Merchant selection is then
restricted to configured ordinary shops around Narootuh.
Unseen merchants use the same bounded discovery approach as quest NPCs; a blocked
close approach may retry within the server's 64-pixel conversation range.
Missing or unreachable merchant configuration, or an unanswered shop-list request,
pauses autonomy with an explicit reason. Both server and manager packages must contain matching
`config/server/shops` definitions; a city teleport cannot enable a server without shops.

The roster reports the current activity or waiting reason. Bounded route searches,
missing catalogs, unsupported quest actions or unavailable merchants can prevent
a goal from being completed; city and validated spawn-area travel are the automatic
test-control exceptions described above.

## Open and close a spectator view

Set **Client executable** to the rebuilt `openkal_client` and optionally select
the normal client profile. Select a character and click **Watch player**. The
manager logs it in if necessary and starts the normal client against a private
local Unix-domain bridge. Account UI and character selection are skipped.

The graphical view watches the already connected character while autonomous play
continues. It launches the ordinary client in the general
`OPENKAL_SESSION_READ_ONLY=1` mode. Camera look and zoom, hover information and
inspection shortcuts remain available; gameplay inputs and outgoing gameplay
requests are disabled. The manager also discards spectator gameplay packets, so
a modified view cannot take over the session. Movement and actions are presented
from server confirmations using the same interpolation as remote players. Final
movement segments finish before idle begins; teleports and authoritative
corrections snap immediately. Observed feet use the existing standing-surface
query to prevent display below loaded terrain or a nearby deck. Confirmed heights
above the surface are preserved, and this presentation never sends height changes
to the server. Close and reopen the window at any time. Its world
entity is preserved; no second account login occurs.
Different characters may have separate windows; a character can have only one
spectator window. Finish a trade or pending teleport before attaching a view.

The manager owns the real TLS connection throughout. On attachment, the bridge
forwards the viewer's ordinary challenge response so the server can send a fresh
authoritative snapshot. A handshake challenge alone is not a position; the view
waits for an authoritative pose before applying observed movement. The
bridge lives in an owner-only temporary directory and disappears with the tool.
The game view remains a normal client and can still receive damage or die.

## Verification

```bash
cmake --build build-test-players \
  --target openkal_test_population openkal_test_player_agent_test \
    openkal_test_multiplayer_presentation openkal_test_player_integration -j
ctest --test-dir build-test-players \
  -R '^(test_population|test_player_agent|test_players_ui|multiplayer_presentation)$' \
  --output-on-failure
```

With an isolated-test-capable PostgreSQL DSN, the integration test creates and
removes its own schema and uses project-owned map/item fixtures:

```bash
export OPENKAL_TEST_POSTGRES_DSN='host=127.0.0.1 dbname=YOUR_DB user=YOUR_USER password=YOUR_PASSWORD'
ctest --test-dir build-test-players -R '^test_player_integration$' --output-on-failure
```

It exercises 51 simultaneous TLS players, eight guilds, repeated provisioning,
leadership changes in both directions, live inventory, missing starter-weapon
recovery for online and offline players without duplicate grants, scattered teleports,
and graphical attachment, rejected spectator movement and detachment using the real bridge protocol.
The Qt smoke test renders without game assets. Testing the actual 3D appearance
and all graphical actions still requires compatible local runtime data.

The agent test uses project-owned synthetic maps, terrain, items, NPCs, quests and
skills under GPL-3.0-or-later, packaged in an owned `config.pak` fixture. It checks
archive-only catalogs overriding loose definitions, packaged area maps, profile
and environment selection, relative external asset paths, missing-package errors,
route detours and corner clearance, coarse and fine routes through narrow passages,
collision-only outdoor bridges over blocked terrain, rejected high roofs and
missing bridge geometry, offset bridge approaches over blocked riverbeds, narrow
bridge entrances between coarse cells, distant quest routes, paced straight and diagonal
movement, speed bonuses and slows, buff expiration, stalled acknowledgements,
confirmed correction of stale standing heights from above and below, settling on
higher decks, bridges extending from neighboring map cells, rejected height corrections,
nonrepeating failed quest searches, validated spawn-area fallbacks, matching arrival
confirmation, blocked landing points, cancellation and rejection, unlimited travel to every regular city without
scroll items, teleport confirmation, cancellation and timeout, blocked NPC and
merchant city recovery without repeated teleports, loot before quest travel,
combat priority with multiple attackers, pickup after the last attacker dies, survival priority,
ordinary equipment replacement, quest requests, NPC dialog proximity and lifetime,
blocked spawn centers and edges, nonrepeating failed spawn probes, skill timing,
sales protection and read-only input. Its end-to-end phase connects the same
agent to an ordinary SQLite-backed local server with test control disabled,
lowers an initially floating player to the floor, completes an item-delivery quest
with persisted currency and a migrated medicine reward, picks up a
normally dropped item, walks to monsters and earns combat experience. The inventory
server test also covers initial-definition precedence, missing replacements and
full-inventory rejection without partial rewards or lost delivery items. Local Unix socket
binding must be permitted when running the server-backed tests.

Set `OPENKAL_TEST_PLAYER_SOAK_SECONDS=60` when running the integration test to
check an additional minute with all 51 sessions idle and connected. Longer
values (up to 3600) can be used with an appropriate CTest `--timeout` override.
