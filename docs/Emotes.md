# Character emotes

The later client asset pack stores the twenty regular character emotes as
action `10`. Each supported human class has a matching motion family:

```text
Model/Motion/T{class}_10_A_{emote:02}.gb
```

The class letters used by OpenKal are `w` (Knight), `r` (Archer), `m` (Mage),
and `t` (Thief). The emote sub-indices follow the published character-motion
order:

1. Bow
2. Yes
3. No
4. Laugh
5. Hug
6. Excitement
7. Angry
8. Yawn
9. Best
10. Clap
11. Hand
12. Cheers
13. There
14. Provocation
15. Dance
16. Showoff
17. Forward
18. Kiss
19. Bashfulness
20. Drink

Reference: [KalOnline character motion](https://gameagit.com/kalonline/Motion)

Click an emote in the skill window's Action tab, or drag it onto a numbered
hotbar slot and click that slot or press its hotkey. Emotes play once and return
to idle; movement interrupts them. Binding, clicking, dragging, and restoring
an emote never replaces the active mouse-action skill. Existing saves with an
emote in that slot are repaired on load. Chat commands are not implemented.

Weapons and shields, including their shadows and attached weapon mix effects,
are hidden during emotes. They reappear when the emote finishes or is interrupted;
the equipped items remain unchanged. The same mesh visibility applies to remote players.

Emotes require an idle, living human character. Resting, riding, fishing,
transformation, and active interaction or combat poses take precedence. A missing
motion is reported in the client log without substituting a combat animation.
Motion files are loaded on demand, including lowercase action-letter variants.
Authored sound cues use the existing animation sound scheduler.

The shared Action-tab shortcut range `2022..2041` maps in order to action-10
motions `1..20`. This is the runtime input contract for optional user-maintained
JSON catalogs; no external catalog or motion assets are redistributed here.
Common riding remains separate and uses `T{class}_0_A_04.gb`.

OpenKal uses the existing `PlayerAnimation` opcodes with an independently designed
payload: C2S contains one motion byte; S2C contains the authoritative player ID
(u32) followed by that byte. Exact payload lengths and motions `1..20` are
validated. The server accepts requests only from living, available characters,
limits broadcasts to one every 250 ms, and sends them to players in sight on the
same map, including the requester. Emotes do not consume MP or occupy combat
cooldowns. These payloads describe OpenKal's interface, not a claim about an
external server's protocol.

Project-owned regression tests cover all twenty distinct skeletal motions for all
four human classes, one-shot completion, replay, movement interruption, UI
clicks and dragging, saved shortcuts, packet validation, and server round trips.
Fixtures are generated by the tests; no external assets are used.
